# 测试执行平台绿地设计文档集

> [!IMPORTANT]
> **这是设计文档，不是已交付能力的说明。**
>
> 本目录描述的领域模型、状态机、Worker 协议和调度设计，绝大部分只以领域层代码 +
> 测试替身（Fake）的形式存在，**尚未接入真实运行时流量**。仓库中当前可实际运行的，
> 是控制面直连 Docker 的单宿主实现（见根目录 `README.md` 与 `docs/FEATURES.md`）。
>
> 文档中出现的 `VERIFIED` / `MET` / `CLOSED` 等字样，指的是「该设计切片的领域层契约
> 已由测试覆盖」，**不代表对应功能在运行时可用，也不代表可用于生产**。

## 本目录包含什么

这套设计当初按「需求 → 架构 → 详细设计 → 实现契约 → 实施计划 → 验收证据」的顺序
展开过十余份文档。随仓库发布的是其中设计密度最高、对读者最有参考价值的三份：

| 文档 | 类型 | 内容 |
|---|---|---|
| [演进式架构设计](03_ARCHITECTURE_DESIGN.md) | Architecture | 系统边界、控制面与 Worker 的信任域划分、从单机 MVP 到多 Worker 的演进路径 |
| [详细设计](04_DETAILED_DESIGN.md) | Design Reference | 核心领域模型、状态机、Worker 协议、调度与安全控制的具体设计 |
| [M0 状态模型实现契约](10_STATE_MODEL_CONTRACT.md) | Implementation Contract | Run/Attempt/Batch 的状态、命令、聚合、持久化与迁移必须遵守的实现契约 |

其余文档属于内部过程记录，未随本仓库发布，包括：需求规格、现状对比评估、实施计划、
需求追踪矩阵、各阶段决议与签署包、实施状态账本，以及逐 milestone 的验收证据账本。
保留文档中对它们的引用因此指向不存在的文件，这是有意为之，不是链接失效。

## 与其他文档的关系

- 产品方向的唯一权威源是 [`docs/DIRECTION.md`](../DIRECTION.md)，本目录不重新定义方向。
- 当前**已实现**能力见 [`docs/FEATURES.md`](../FEATURES.md)；本目录描述的是目标设计。
- 当前实现的分层结构见根目录 [`ARCHITECTURE.md`](../../ARCHITECTURE.md)，
  与本目录的绿地架构设计是两回事：前者描述代码现状，后者描述目标形态。
