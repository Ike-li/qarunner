## 1. 背景与目标

### 1.1 要解决的问题

团队有 pytest / Playwright 回归套件，但常见情况是：

1. 跑测入口散（本机、零散脚本、聊天群贴日志），结果难复用。
2. 只能看「这一次过没过」，难判断相对上次是**新挂、修好、还是老 flaky**。
3. 需要定时回归，又不想上完整 CI/QA 平台。
4. 测试代码和依赖在宿主上直跑，风险和误操作成本高。

### 1.2 价值链与产品目标

回归测试的唯一产出是**信号**（「变更后，已有行为是否仍成立」）；信号只有**可信**（噪声可辨）且**被人消费**（看到→解读→行动）才产生价值。产品目标沿这条价值链设立：

```
执行(产原料) → 调度(原料持续) → 报告(原料可读) → 回归视图(原料→信号) → 触达(信号→行动)
                                        ↘ 信号维护(抗腐烂)：flaky 检测（处置在套件侧，见 AS-7）
```

| ID | 目标 | 合格判据 | 度量锚 |
|----|------|----------|--------|
| GO-1 | 套件接得进、跑得动 | 新套件从接入到首个终态 Run 全程在平台内完成，无需改平台代码（V1） | [`METRICS.md`](METRICS.md) #4 时长、#5 跑量 |
| GO-2 | 配置可复用、可定时 | 同一 Profile 可反复一键触发、可被调度引用，cron 到点自动出 Run（V1） | METRICS #5 |
| GO-3 | 结果可解释 | 任一失败 Run 不出平台即可定位到用例级失败与日志/报告证据（V1） | — |
| GO-4 | 跨次可对比 | 同范围两次 Run 能区分新增失败 / 已修复 / 持续失败，可疑用例可查历史（V2） | METRICS #1、#2 |
| GO-5 | 默认更安全 | 唯一执行形态为容器；任何越权读写被拒（V3、V4） | — |
| GO-6 | 部署够简单 | 按 [`deployment.md`](deployment.md) 标准路径完成单节点部署且健康检查通过（V6）；可选能力全关不影响主路径（V5） | — |
| GO-7 | 回归信号可信 | 失败可归因：新挂/修复/持续/flaky 四类判定口径写死（§3.3）且不误导（无基线不乱分桶）（V2） | METRICS #2（阈值校准见 OP-1） |
| GO-8 | 信号被消费 | 失败不必等人翻列表：登录落地页即见（V1）；配置了通知渠道时终态主动触达（V5） | METRICS #6、#7（观察期） |

### 1.3 一句话（引用方向，不扩写）

自托管、单节点的测试执行 + 调度 + 回归对比服务。完整表述见 [`DIRECTION.md`](DIRECTION.md)。

### 1.4 范围

| 做 | 不做 |
|----|------|
| 接入套件、执行、调度、报告与日志、跨次对比 | CI 流水线、用例库/缺陷管理 |
| 账号与对象权限、Web 控制台 + API | 多租户 SaaS、组织/项目空间 |
| 可选：飞书通知、AI 失败诊断 | AI 自动改代码、多活水平扩展（默认形态） |

## 2. 使用对象与权限

### 2.1 谁用：三个决策场景 × 权限角色

需求的优先级论证以**决策场景**为依据（同一人可占多个场景）：

| 场景 | 要回答的问题 | 依赖的能力 | 最敏感的属性 |
|------|--------------|------------|--------------|
| 合前门禁 | 「我这次变更能不能合？」 | 即席/一键触发、实时日志、汇总（RN、RP-1/4） | 反馈时长（METRICS #4） |
| 套件守护 | 「套件还健康吗？在腐烂吗？」 | 调度、趋势、flaky、diff（SC、DF） | 信噪比（GO-7） |
| 排障 | 「这个失败为什么发生？」 | 日志、产物、用例历史、AI 诊断（RP、DF-5、AI） | 证据完整性 |

系统权限按**角色**划分（与场景正交）：

| 角色 | 典型工作 | 系统权限 |
|------|----------|----------|
| 测试/开发（user） | 接入套件、配 Profile、触发/定时跑、看结果与对比 | 只管理自己的资源 |
| 管理员（admin） | 开账号、清磁盘、看全量数据、排障 | 全局能力 + 用户管理 |
| 运维 | 部署、备份、配环境变量 | 部署面；应用内通常用 admin |
| 脚本/集成 | Token 调 API | 与对应用户权限相同 |

### 2.2 权限总规则

1. **所有者范围**：user 只能读写自己名下对象——Suite、Credential、Profile、Run、Schedule，及其派生数据（diff 基线、趋势、用例历史）。
2. **列表**：user 只看到自己的，不报错。
3. **单条越权**：他人资源不能读改；「没权限」与「不存在」可区分（码表见 API 文档）。
4. **admin**：可跨用户查看与管理（能力枚举见 [`FEATURES.md`](FEATURES.md) §8：用户 CRUD、产物清理、跨用户查看）。
5. **登录**：用户名 + 密码；之后用 Bearer Token 或同源 Cookie。
6. **禁止**：URL 查询参数带 Token 当认证。
7. **生产**：UI 与 API **同源**；Cookie 为 HttpOnly + SameSite=Strict，并开启 Secure（HTTPS）。

### 2.3 账号管理

| 能力 | 要求 |
|------|------|
| 登录 / 登出 / 当前用户 | 必须有；Token 有效期可配（默认 24 小时） |
| 会话失效 | 登出、改密、角色变更**必须使该用户全部存量 Token 失效**（旧 Token 随后请求返回 401） |
| 用户 CRUD（角色、密码） | 仅 admin |
| 删自己 | 禁止 |
| 去掉最后一个 admin（降级或删除） | 禁止 |
| 登录防爆破 | 同「用户名 + IP」连续失败达阈值（默认 5 次，可配，0=关闭）后指数退避锁定（60 秒起，上限 900 秒） |

## 3. 术语与核心对象（读需求前先对齐词）

### 3.1 核心对象

| 对象 | 含义 | 关键关系 |
|------|------|----------|
| 套件 Suite | 接进来的测试代码（Git 或本地） | 被 Profile / Run 引用 |
| 凭证 Credential | 私有仓 Token | 仅元数据可见，secret 不回显 |
| 配置档 Profile | 「怎么跑」的配方 | 可一键触发；可被调度引用；可挂通知地址；**删除连带删除其全部 Schedule（BR-11）** |
| 运行 Run | 一次异步执行及结果 | 来自即席参数 / Profile / 调度 / 重跑 |
| 调度 Schedule | cron + 时区 + 绑定 Profile | 到点或手动立即触发产生 Run |
| 用例结果 | 单条用例在某次 Run 的结果 | 支撑 diff / 历史 / flaky |

### 3.2 Run 状态机

排队中（queued）→ 执行中（running）→ **终态**：完成（completed）| 失败（failed）| 超时（timeout）| 已取消（cancelled，含停机中止的在途 Run）。
终态不可再取消、不可再迁移。

### 3.3 关键术语（判定口径，与源码一致）

| 术语 | 精确定义 |
|------|----------|
| **同范围** | 两次 Run 的 `profile_id`、套件路径、runner、编译后参数（marker / 选中文件 / 附加参数在创建时折叠进参数串）**四者完全一致**。同一套件同参数下，走 Profile 与即席运行互不同范围 |
| **基线** | 与本次 Run 同范围、状态为「完成」、创建时间早于本次的**最近一次** Run；不存在则「无基线」 |
| **失败** | 用例状态为 failed 或 error；skipped 与 passed 不算失败（diff 与 flaky 同口径） |
| **flaky（不稳定）** | 同一用例（套件+名称）按时间序把状态二值化为失败/非失败后：观测次数 ≥ 4 **且**相邻翻转次数 ≥ 3（两阈值均可配）。单调劣化或单次「挂→修」不算 |
| **即席运行** | 不经 Profile、直接以参数创建的 Run |
| **在途** | 状态为排队中或执行中的 Run |

## 4. 主路径（必须跑通）

以下三条是验收底线。细节表见第 5 节。

### 4.1 首次跑通

接入套件（Git 或本地）→ 套件声明了依赖时（如含 `package.json`）准备依赖 → 建 Profile → 触发 → 进入终态 → 能看汇总与日志/报告。

### 4.2 日常回归

定时或手动触发同一 Profile → 与上次**同范围**结果对比 → 能分清新增失败 / 已修复 / 持续失败 → 可疑用例能看历史是否反复跳。

### 4.3 权限不串

用户 A 的 Run、配置、凭证、对比基线数据，用户 B 不可见、不可用。

## 5. 功能需求

「合格标准」是测试与评审依据；默认由自动化测试验证（§0.3 约定）。

### 5.1 套件接入（SU）— P0/P1

| ID | 需求 | 优先级 | 说明 | 合格标准 |
|----|------|--------|------|----------|
| SU-1 | 列出套件 | P0 | 看到可跑集合 | 登录后可列出 |
| SU-2 | Git 接入 | P0 | 浅克隆指定 ref；可绑凭证 | 合法仓成功；非 `https://` / `git@` 形态一律拒绝 |
| SU-3 | 本地接入 | P1 | 链本地目录；信任前提见 AS-8 | 合法路径（= 平台进程可见文件系统内的既有目录，容器部署时即挂载树）成功；不存在的路径明确失败 |
| SU-4 | 更新 | P1 | Git pull（复用绑定凭证） | 仅所有者或 admin；更新后套件内容可观察变化；失败明确报错 |
| SU-5 | 准备依赖 | P1 | 含 `package.json` 的套件执行 `npm ci` | 失败必须明确失败 |
| SU-6 | 文件树与标记 | P1 | 选文件、pytest marker / Playwright tag | 选中文件/标记后，Run 的实际执行范围与选中范围一致 |
| SU-7 | 删除 | P1 | 删套件 | 仅所有者或 admin；删后不可见 |
| SU-8 | 路径安全 | P0 | 防穿越 | 套件名含 `/`、`\` 或前导 `.` 被拒；危险路径不能执行到未授权内容 |

### 5.2 凭证（CR）— P0/P1/P2

| ID | 需求 | 优先级 | 说明 | 合格标准 |
|----|------|--------|------|----------|
| CR-1 | 保存 HTTPS Token | P1 | 私有仓用 | 加密存储 |
| CR-2 | secret 不回显 | P0 | 查询永不返回明文 | 任何响应不含密钥 |
| CR-3 | 安全注入 | P0 | 用于 clone/pull | 不进命令行参数、URL 与平台日志 |
| CR-4 | 所有者范围 | P0 | 各用各的 | 不能用别人凭证 |
| CR-5 | 删除的悬挂语义 | P1 | 删除被引用凭证后 | 引用它的套件更新明确失败（不静默降级为匿名拉取） |
| CR-6 | 轮换路径 | P2 | 平台不提供原地更新 | 轮换 = 删除 + 重建可完成；文档化该路径即合格（人工评审） |

### 5.3 执行配置 Profile（PF）— P0/P2

| ID | 需求 | 优先级 | 说明 | 合格标准 |
|----|------|--------|------|----------|
| PF-1 | 增删改查 | P0 | 保存跑法；删除行为见 BR-11 | 所有者可管；他人不能读改；删除连带删除其 Schedule |
| PF-2 | 一键触发 | P0 | 按配方建 Run | 新 Run 关联该 Profile |
| PF-3 | 通知地址 | P2 | 飞书 Webhook | 仅 `https://`；主机名为环回/私网**字面量**（IP 前缀与已知内网主机名清单）的拒存；**不做 DNS 解析**（残余面登记 RK-6） |

Profile 至少能表达：套件、runner、选择范围（文件/标记）、附加参数、环境变量、超时。（接口中的执行器字段为兼容保留，见 BR-1。）

### 5.4 执行 Run（RN）— P0/P1

| ID | 需求 | 优先级 | 说明 | 合格标准 |
|----|------|--------|------|----------|
| RN-1 | 异步执行 | P0 | 提交即受理 | 有排队/执行中，最终唯一终态 |
| RN-2 | 即席参数 | P0 | 不建 Profile 也能跑 | 危险参数/路径拒绝 |
| RN-3 | 容器执行 | P0 | **唯一执行形态**（BR-1） | 全部 Run 的执行器为 docker；隔离底线见 NF-3 |
| RN-5 | pytest + Playwright | P0 | 两套 runner | 均有用例级汇总；Playwright 产物平台内可取 |
| RN-6 | 取消 | P0 | 停掉在途任务 | 终态=已取消；进程/容器终止、并发槽释放 |
| RN-7 | 重跑 | P1 | 按原参数新建 | 新 ID；原记录不变 |
| RN-8 | 全局并发受限 | P0 | 防止打满宿主 | 同时执行数不超上限（默认 4，可配，取值 ≥1；0/负值未定义）；到限的新 Run 排队而非丢弃 |
| RN-9 | 单用户在途上限 | P0 | 防单人刷爆 | 在途数超上限（默认 20，可配，0=不限）即拒绝并返回限额错误；admin 豁免 |
| RN-10 | 超时 | P0 | 防挂死 | 单次 Run 超时可配，默认 30 分钟；**单次请求上限 24 小时**；全局默认值由运维配置（不受 24h 校验约束，属运维可信面）。达到超时进入超时终态 |
| RN-11 | 查询列表/详情 | P0 | 含汇总、状态、起止时间、日志尾 | 按所有者规则 |
| RN-12 | 锁定 | P1 | 保护关键证据 | 清理跳过锁定 |
| RN-13 | 删除 Run | P1 | 删记录与产物 | 在途或锁定不可删（冲突错误）；删除彻底 |
| RN-14 | 清理产物 | P1 | admin 按保留天数清 | 非 admin 不能清；只清未锁定过期项的物理产物，元数据保留 |
| RN-15 | 崩溃恢复 | P0 | 单实例重启 | 重启后：**执行中**遗留标为失败；**排队中**遗留自动续跑；无永久在途 |
| RN-16 | 优雅停机 | P1 | 尽量落盘 | 停机有缓冲期（默认 30 秒，可配）；缓冲内完成的 Run 数据一致；**超出缓冲的在途 Run 以已取消或失败终态收敛，不得停留在途** |

**Playwright 产品约定**：结果与产物目录由平台接管，用户参数不得把产物写到平台管不到的地方。

## 6. 关键业务规则（BR，容易扯皮，写死）

| ID | 主题 | 规则 |
|----|------|------|
| BR-1 | 执行形态 | **唯一执行形态 = docker 容器**；接口中的执行器字段为兼容保留，不改变实际形态 |
| BR-2 | 套件独占 | user 不得对他人名下套件执行/更新/准备/删除；admin 不受限 |
| BR-3 | 对比范围 | 只有「同范围」（§3.3）才出 diff；范围不同 = 无基线 |
| BR-4 | 失败定义 | failed / error 算失败；skipped 不算（diff 与 flaky 同口径） |
| BR-5 | 可选能力无害（P0） | AI、通知关闭、失败或超时，**不得**阻断跑测、状态落库与查结果 |
| BR-6 | 单节点语义 | 崩溃恢复、调度去重按单实例拥有数据库设计；默认不承诺多副本 |
| BR-7 | 同源约束 | 浏览器 Cookie 登录只承诺同源部署形态 |
| BR-8 | 密钥门禁 | 空/弱密钥与弱管理员密码拒绝启动 |
| BR-9 | 无基线不误导 | 无可比基线时明示「无基线」，禁止把全部用例判成「新增」 |
| BR-10 | 套件内容版本语义 | **Run 使用触发时刻磁盘上的套件内容，平台不自动拉取更新**；更新须显式执行 SU-4（「调度前自动 pull」为开放项 OP-4） |
| BR-11 | Profile 级联删除 | **删除 Profile 连带删除其全部 Schedule**；用户由此丢失对应定时任务属预期行为，UI/API 文档须可见此后果 |

## 7. 非功能需求（NF）

### 7.1 安全

| ID | 要求 |
|----|------|
| NF-1 | 启动安全门：密钥/管理员密码缺失、弱值或已知占位值 → 拒绝启动（即 BR-8） |

## 8. 假设与依赖（AS）

违反假设时，产品不承诺对应能力；部署方须自行评估。

| ID | 假设/依赖 | 违反时的后果 |
|----|-----------|--------------|
| AS-1 | 宿主 Docker daemon 可达是**硬依赖**（唯一执行形态，BR-1） | 平台可启动、可查历史，但**无法执行任何测试（无退路）** |
| AS-2 | 单实例部署（崩溃恢复、调度去重按单实例语义设计） | 多副本需自行保证仅一副本开崩溃恢复；属超出承诺的形态 |
| AS-3 | 部署面受信：平台进程可达 docker socket，**编排层沦陷≈宿主 root**；真正的隔离边界是执行容器，不是平台进程；平台自身不在宿主进程内运行被测代码（BR-1） | 平台自身暴露在不受信网络时，须由部署层（反代/网络策略）另行加固 |
| AS-4 | 浏览器登录依赖 UI 与 API 同源部署（BR-7） | 跨源部署下 Cookie 登录不可用 |
| AS-5 | 可选外部依赖按需可达：LLM API（AI 诊断）、飞书 Webhook（通知）、Allure 二进制（HTML 报告） | 对应能力降级或关闭，主路径不受影响（BR-5、RP-3） |
| AS-6 | 宿主时钟与 IANA 时区数据正确 | cron 触发时间不可信 |
| AS-7 | flaky 的**处置**（打标记/隔离/重写/删除）在套件代码侧完成；平台只负责检测与展示，不管理用例（DIRECTION 边界） | 期待平台隔离 flaky 用例的诉求见 OP-3（方向级开放问题） |
| AS-8 | 本地接入（SU-3）信任前提：登录用户对平台进程可见的挂载目录树**等同受信**；非容器部署时该范围即宿主文件系统 | 部署方须按此收敛挂载面；不可接受时禁用本地接入、仅走 Git 接入 |

## 10. 风险与开放项

### 10.1 风险登记（RK）

| ID | 风险 | 影响 | 缓解 / 接受理由 |
|----|------|------|------------------|
| RK-1 | flaky 阈值（4 观测/3 翻转）为保守默认，未经真实数据校准 | 误报/漏报不稳定用例 | 阈值可配（§7.5）；积累生产数据后回看（OP-1） |
| RK-2 | DooD 信任边界：平台进程持有 docker socket，等效宿主 root（AS-3） | 平台进程沦陷即宿主沦陷 | 平台输入面硬化（NF-3～NF-6）+ 部署面收敛；残余风险在「受信部署面」定位内接受 |
| RK-3 | 单节点单点故障 | 宕机期间调度不触发、结果不可查 | 可整体备份（NF-17）+ 快速重建；定位内接受（NF-14） |
| RK-4 | AI 外发面：失败日志片段外发 LLM 供应商，可能含敏感信息 | 数据外泄面扩大 | 默认关闭（Key 空）；日志截断 16KB；限流；可指自建网关（AI-5） |
| RK-5 | SQLite 单写者：高并发写吞吐受限 | 超大团队/高频场景变慢 | 单节点小团队定位内接受；超出即触发方向级变更（NF-14） |
| RK-6 | Webhook 校验为字面量级（PF-3/NF-4 不做 DNS 解析） | 解析到内网地址的公网域名可通过校验，构成 DNS 重绑定式盲 SSRF 残余面（发起方为持 docker socket 的平台进程） | 出网仅 POST 通知卡片、响应不回显；候选加固=解析校验+发送前复检（实现级变更，按 §0.4 走评审） |
| RK-7 | 日志/产物驻留敏感信息：被测代码可把 env 密钥打印进持久化日志（RP-4）与产物（RP-5），并随备份扩散（NF-17 不加密） | 秘密驻留与扩散 | 处置立场：**不承诺脱敏**；访问由所有者范围控制覆盖（§2.2、RP-5）；备份保密性等同部署面。套件作者须自律不打印秘密 |
| RK-8 | 可问责性缺口：除登录失败日志外，破坏性/特权操作（用户 CRUD、删除、清理）无「谁在何时做了什么」的动作审计轨 | 对 DooD≈宿主 root 的工具，事后追责能力弱 | §9.7 排除的是完整审计中台，不排除最小动作审计；候选需求登记 OP-5 |

### 10.2 开放项（OP，不阻塞当前基线）

| ID | 事项 | 处理 |
|----|------|------|
| OP-1 | flaky 默认阈值待真实数据校准 | 先可配置，积累数据后校准（挂 RK-1） |
| OP-2 | `FEATURES.md` 待补「通知」能力小节 | 后续文档任务 |
| OP-3 | 视图层 flaky 豁免（diff/通过率可排除已标记用例） | **方向级开放问题**：涉及「检测→处置」边界（AS-7/DIRECTION），待方向讨论，不进入本基线 |
| OP-4 | 调度前自动更新套件（pre-pull） | 需求候选：解决 BR-10 下「定时回归跑旧代码」的预期落差；待评估凭证与失败语义后按 §0.4 走需求级变更 |
