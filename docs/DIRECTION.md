# qarunner 产品方向（SSOT）

> 本文件是 qarunner 产品定位、核心价值、信任边界和产品边界的唯一权威源。
> 其他文档只能引用本文件并展开各自主题，不得重新定义产品方向。
> 方向变更必须先修改本文件，再同步需求、能力、架构和发布文档。

版本：v2.4.2
状态：评审中
更新日期：2026-07-12

## 1. 核心问题

目标团队已经拥有 pytest 或 Playwright 自动化测试，但缺少一个低运维成本的统一控制面，能够安全地执行这些测试、保存完整证据，并判断本次结果相对历史到底发生了什么变化。

单纯“把测试跑起来”没有形成产品价值。只有当一次运行可追溯、两次运行确实可比较、失败证据足以支持下一步行动时，测试结果才是可信的回归信号。

## 2. 一句话定位

qarunner 是面向受信内网单团队的自托管回归运行服务：单个控制面负责调度和证据管理，单个专用加固 Worker 主机以每 Run 全新一次性容器执行 pytest 和 Playwright，并只在执行口径等价时生成可信的跨次回归判断。

## 3. 目标用户

- 主要用户：负责维护自动化回归套件和解释失败结果的 QA、测试开发或质量负责人。
- 次要用户：需要在提交、发布或故障排查前消费回归信号的开发人员。
- 管理用户：负责账号、目标访问授权、网络/Registry 策略、密钥、部署、备份和故障处置的管理员与运维人员。

## 4. 信任模型

- 部署范围：受信内网、单团队使用，不直接暴露公网。
- 管理员与运维人员：可信，能够管理全局账号、网络策略、密钥和部署环境。
- 普通用户：半可信，只能访问和操作自己名下的资源，不能扩大网络或宿主权限。
- 测试代码及其第三方依赖：不可信，必须在隔离执行环境中运行。
- 控制面主机：高价值信任边界，保存 API、数据库、调度、授权和平台密钥，不安装或挂载用于执行测试的 Docker socket。
- 专用 Worker 主机、Worker agent 和本机 Docker daemon：受信执行控制边界，只承载 qarunner 执行工作负载；不能持有控制面数据库凭证、管理员会话密钥或无关业务秘密。
- 每 Run 一次性执行容器及其中的测试代码、依赖和生成器：不可信，不能访问 Worker agent、Docker socket、控制面或其他 Run。
- Git、飞书、AI 服务和真实被测环境：外部依赖，必须通过明确的出站策略访问。
- 网络可达性不等于执行授权：即使目标已加入网络策略，不可信测试代码也只有在管理员批准的不可变目标访问授权范围内才能访问真实被测环境。

## 5. 产品承诺

### 5.1 可复现

每个 Run 必须能够回答：谁在何时，以哪个不可变 Suite Revision/content digest、哪版 Profile 或手工请求口径、哪个依赖快照、哪些参数、哪个执行镜像、哪个目标环境与环境租约、哪项网络策略和哪份适用授权发起了运行。

### 5.2 可比较

只有来源版本、执行配置、环境身份和网络策略满足批准的等价规则时，两次 Run 才能建立基线关系。无法证明等价时，产品必须显示“无可比基线”，不得输出误导性 diff。

### 5.3 可解释

Run 必须保存状态、用例级结果、日志、报告、产物和冻结后的 Evidence Manifest。平台执行故障、测试失败、跳过、环境清理失败和取消必须是不同语义，不能混为一个“失败”。

### 5.4 可行动

用户应能从失败信号进入证据、历史和重跑路径。调度漏跑、授权阻断、执行能力不可用和证据缺失必须可见，不能静默发生。

### 5.5 受控执行

pytest 和 Playwright 均在 Docker 执行环境中运行：

- 控制面只创建、授权、调度和跟踪 Run，不执行测试代码、依赖安装、Git 处理或报告生成，也不直接访问 Worker Docker daemon。
- V7 固定为一个控制面实例和一台专用加固 Worker 主机；Worker agent 通过受认证协议领取冻结任务并在本机创建容器。
- 每个 Run 必须创建全新的、不可复用的一次性 executor 容器；终态后销毁，销毁失败进入健康降级且不得复用。
- 默认使用 isolated 网络模式，禁止出站访问。
- Git clone/fetch 与工作区物化必须在 Worker 上的独立 Source Acquisition 容器完成，不能在控制面处理不可信仓库。
- 依赖准备必须在 Worker 上的独立受限容器中完成，只能访问批准的软件源，并生成可追溯的依赖快照。
- 报告生成必须在 Worker 上的独立受限容器完成；控制面只接收受限结构化结果和可校验证据。
- Playwright 可使用 approved-target 模式访问真实被测环境。
- approved-target 必须绑定管理员批准的 Docker 网络或目标白名单。
- 真实环境 Run 还必须绑定 Target Access Grant；授权至少固定不可变 Suite Revision、Profile revision/手工请求口径、依赖快照、目标环境、网络策略和密钥引用版本。
- 上述任一授权维度变化后，旧授权立即失效，普通用户不能通过替换代码、参数或密钥继承原授权。
- Grant 批准只代表允许该不可变组合访问目标，不改变测试代码及依赖“不可信”的分类。
- 生产环境不是默认 Target Environment；在产品、安全和运维专项批准前必须拒绝生产目标授权。
- 普通用户不能自行扩大允许访问的网络范围。
- Run 必须记录所使用的网络策略版本和目标环境标识。
- 共享真实环境必须使用原子 Environment Lease、并发/命名空间与清理策略，避免不同 Run 相互污染。
- 报告、日志、trace 和其他产物均视为不可信内容；主动内容不得与控制面会话共享同一安全上下文。

## 6. 产品支柱

1. 受控执行：控制面与专用 Worker 分离、每 Run 一次性容器、依赖准备沙箱、资源限制、默认断网、目标访问授权和批准目标网络。
2. 持久调度：即时与 cron 触发、可恢复队列、重复触发防护和漏跑可见性。
3. 完整证据：用例结果、实时日志、报告、截图、录屏、trace 和运行来源。
4. 可信回归：基线等价判断、差异分类、趋势、用例历史和不稳定识别。

可信回归是差异化内核；执行、调度和证据是它成立的前提。

## 7. 产品边界

- 不是 CI 流水线：允许 Git 套件接入和更新，但不处理代码仓库事件触发、多阶段构建、制品发布或部署编排。
- 不是测试管理平台：不维护人工测试用例库、测试计划、需求关联或缺陷生命周期。
- 不是多租户 SaaS：不提供组织、项目空间、租户隔离、计费或公网自助注册。
- 不是高可用或弹性执行集群：V7 只承诺一个控制面实例和一台 Worker 主机，不提供多 Worker 调度、自动扩缩容或故障自动切换。
- 不是通用代码执行平台：只允许受支持的测试 Runner 和受控参数。
- 不是测试逻辑正确性证明系统：平台证明输入、执行口径和证据完整性，但不能证明测试断言、测试数据或测试作者结论本身正确。
- 不是高保证恶意代码沙箱：每 Run 容器仍共享 Worker 主机内核。V7 接受“专用加固 Worker + 一次性容器”的残余风险；公网、多租户、生产 SUT 或高对抗代码必须重新评审并升级到每 Run VM/microVM 等独立内核方案。
- 不是自动修复系统：AI 只能提供只读、可选的辅助诊断，不修改测试或业务代码。
- 不是完整审计或监控产品：但多用户共享和生产运行所需的最小安全审计、健康检查和告警属于产品底线。

## 8. 核心与扩展

### 8.1 核心基线

- 隔离的源码获取、不可变 Suite Revision 快照与来源标识。
- 隔离的依赖准备、依赖快照和批准软件源。
- 单控制面到单专用 Worker 的认证调度协议、Worker 身份/健康/drain 和任务 fencing。
- Profile、即时运行、重跑和持久队列。
- pytest 使用 isolated；Playwright 仅在持有有效 Target Access Grant 时才能访问批准目标。
- Target Environment readiness、Environment Lease、测试数据命名空间和清理状态。
- 幂等触发、用例级结果、Evidence Manifest、报告和产物，以及不可信主动内容的隔离交付。
- 基于完整 provenance 的回归比较。
- cron 调度、漏跑可见性和执行健康。
- 认证、owner scope、密钥引用和最小操作审计。
- 控制面与 Worker 分离部署、备份恢复、Worker 重建和容量保护。

### 8.2 扩展能力

- 飞书等通知适配器。
- 趋势与质量看板。
- 中英文和明暗主题。
- 受限的本地目录接入。
- AI 失败诊断。

扩展能力不得成为核心执行、证据和回归判断的依赖。
